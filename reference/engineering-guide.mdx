## Repositories and cutover

| Repo | Status |
|------|--------|

## Local setup summary

```bash
git clone git@github.com:Doubt-Productions/doubt-bot.git
cd doubt-bot
cp .env.example .env
yarn setup          # install + generate + migrate dev
yarn dev            # development
yarn test && yarn lint
yarn build && yarn start
```

Required env: `DISCORD_TOKEN`, `DISCORD_CLIENT_ID`, `DISCORD_GUILD_ID`, `DATABASE_URL`, `DEVELOPER_DISCORD_IDS`.

## Prisma migrations

Postgres schema changes use **`prisma migrate`**:

| Command | Use |
|---------|-----|
| `yarn prisma:migrate:dev` | Create/apply migrations in development |
| `yarn prisma:migrate:deploy` | Apply pending migrations in staging/production |
| `yarn prisma:migrate:status` | Inspect migration history |
| `yarn prisma:generate` | Regenerate client after schema edits |
| `yarn prisma:push` | **Local experiments only** — bypasses migration history |

Production and staging: prefer **`yarn setup:prod`** (`generate` + `migrate deploy`).

<Warning>
Do not use `db push` for production BotStaff cutover. Apply migrations first, then import staff data.
</Warning>

## Docker

Multi-stage `Dockerfile`:

1. **build-runner** — `yarn install`, `prisma generate`, `tsc`
2. **prod-runner** — production deps, generated client, `node build/main.js`

Sample `docker-compose.yml` provides `app` + `postgres:16` with a healthcheck. Set secrets via environment; mount or inject `DATABASE_URL` for external Postgres when not using the bundled `db` service.

Boot command: `node build/main.js` (run migrations in your deploy pipeline before starting the container).

## Application commands

- discordx loads command classes via `@discordx/importer` (`importx` in `main.ts`).
- On ready: `bot.initApplicationCommands()` syncs guild slash commands.
- **`CLEAR_GUILD_COMMANDS_ON_BOOT=true`** — destructive one-time maintenance; clears guild commands for all cached guilds on startup.

Regression test `tests/boot-command-deploy.test.cjs` documents that normal boot must not call `clearApplicationCommands`.

## Guards and staff ACL

- Developers: `DEVELOPER_DISCORD_IDS` (comma-separated).
- Staff commands: `BotStaff` table **or** developer (`canUseStaffCommands`).
- Badge grants do **not** substitute for ACL (`tests/staff-acl-not-badge.test.cjs`).

BotStaff operator order:

1. `yarn prisma:migrate:deploy`
2. Import staff (`yarn migrate:mongo` and/or `/botstaff add`)
3. `/botstaff migrate` for badge re-sync if needed
4. `/botstaff list`

TypeScript **`/botstaff migrate`** does **not** read legacy `moderation.staffRoles` from JS `config.js`.

## Mongo→Postgres data migration

Script: `yarn migrate:mongo` / `yarn migrate:mongo:dry-run` (`scripts/migrate-mongo.ts`).

**Prerequisites**

```bash
yarn prisma:generate
yarn prisma:migrate:deploy
```

**Environment**

| Variable | Purpose |
|----------|---------|
| `DATABASE_URL` | Postgres target (writes) |
| `MONGO_SOURCE_URL` or `SOURCE_DATABASE_URL` | Mongo source (read-only) |
| `DEVELOPER_DISCORD_IDS` | Optional — display-only badge sync during migrate |

**Order (high level)**  
Badge → User → UserBadge → BotStaff / Removal → Welcome / Setup / JTC → Economy / Xp / Afk.

- Skips unused legacy collections (e.g. `chatbots`); reports unknown leftovers.
- Economy duplicates: keeps highest wallet+bank total; conflicts logged to CSV.
- Idempotent upserts on natural keys — safe to re-run after fixing conflicts.

Legacy operators still on Doubt-Discord-Bot should finish BotStaff migration there or via this tool **before** decommissioning Mongo.

## Slash-only / intents

`src/bot.ts` omits Message Content Intent. CI runs `tests/no-message-content-intent.test.cjs`. AFK (`src/events/afkCheck.ts`) must remain compatible with mention-only detection.

## Reserved badges

`ensureReservedBadges()` on ready; `/badge` rejects reserved keys and lookalikes. Staff sync via `botStaffService` + `badgeService`.

## Economy invariants

Economy logic lives in `src/services/economyService.ts` and command handlers under `src/commands/categories/economy/`. Account uniqueness is enforced in Postgres (`@@unique([guildId, discordId])`). When changing `/rob` cooldown or penalty logic, add or update focused tests under `tests/`.

## Legacy differences (Doubt-Discord-Bot)

The JS bot used:

- `src/config.js` + `PRODUCTION` toggle and separate `DEV_MONGODB_URI` / `MONGODB_URI`
- Express health server on `0.0.0.0:8080`
- Manual command validators and `devOnly/` deployment to `handler.guildId`
- Mongo `prisma db push` (no migrate)
- `/botstaff migrate` importing `moderation.staffRoles`
- MessageCollector-based welcome message setup (replaced by **modals** in doubt-bot)

Do not assume those behaviors on doubt-bot without verifying source.

## CI

GitHub Actions on doubt-bot runs `yarn test` and `yarn build` on pushes and PRs.

## Release automation

Legacy Doubt-Discord-Bot may still publish GitHub Releases from `package.json` version bumps. doubt-bot release process follows the private repo's workflows — not documented here.

## Operational pitfalls

- Empty `DEVELOPER_DISCORD_IDS` blocks `/botstaff` and developer tooling.
- Postgres unreachable at boot: commands depending on DB will fail until connectivity and migrations are fixed.
- Do not expose legacy `:8080` health checks — doubt-bot has no Express sidecar.
- After permission or command metadata changes, restart to re-sync guild commands.
